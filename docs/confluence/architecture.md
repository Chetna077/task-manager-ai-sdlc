# Architecture

## Diagram

```
                +-------------------------+
                |        Browser          |
                |  (frontend/public/*)    |
                |  index.html + app.js    |
                +------------+-------------+
                             | fetch() JSON over HTTP
                             v
                +-------------------------+
                |   Express server         |
                |   backend/src/server.js  |
                |   - REST API /api/tasks  |
                |   - serves static files  |
                +------------+-------------+
                             | node:sqlite
                             v
                +-------------------------+
                |   SQLite file            |
                |   backend/db/tasks.db    |
                |   schema: db/schema.sql  |
                +-------------------------+
```

## Components

- **Frontend** — static HTML/CSS/vanilla JS, no build step. Talks to the
  backend only via `/api/tasks` REST endpoints.
- **Backend** — single Express process. Owns validation, the status
  workflow, search/filter/sort query handling, and serves the frontend's
  static assets so the whole app is one deployable process.
- **Database** — SQLite via Node's built-in `node:sqlite` module (stable in
  Node 22.5+, no native compilation, no external DB server to install/run).

## Constraints (recorded during Design phase)

The target machine had no Node.js, Git, or Python pre-installed. Node.js LTS
and Git were installed via `winget` before development started. This shaped
two decisions: use `node:sqlite` (zero extra native dependencies) instead of
`better-sqlite3`/`sqlite3`, and use a plain frontend instead of a
React/webpack pipeline, to minimize `npm install` surface and avoid
Windows path-length failures in `node_modules`.
