# Low Level Design

## File layout

```
backend/
  db/schema.sql        -- DDL, run once at startup if tasks.db absent
  src/db.js             -- opens tasks.db via node:sqlite, exposes query helpers
  src/validation.js      -- validate/normalize task input, throws ValidationError
  src/server.js          -- Express app, routes, static file serving
  package.json
frontend/
  public/index.html      -- markup + <template> for a task row
  public/styles.css
  public/app.js          -- fetch calls, rendering, search/filter/sort state
```

## Key functions

- `db.listTasks({ search, status, priority, sortBy, sortDir })` — builds a
  parameterized `SELECT` with optional `WHERE title LIKE ?`, `AND status = ?`,
  `AND priority = ?`, and a whitelisted `ORDER BY` column to prevent SQL
  injection via sort parameters.
- `db.createTask(input)` / `db.updateTask(id, input)` — both run
  `validateTaskInput` first; both set `updated_at`.
- `db.setStatus(id, status)` — validates `status` against the enum
  (`todo`/`in_progress`/`done`); used for both forward transitions and reopen.
- `db.deleteTask(id)` — hard delete, returns 404 if the id doesn't exist.

## Validation rules (validation.js)

- `title`: required, trimmed, 1–200 chars.
- `description`: optional, ≤ 2000 chars.
- `priority`: one of `low`/`medium`/`high`; defaults to `medium`.
- `status`: one of `todo`/`in_progress`/`done`; defaults to `todo`.
- `due_date`: optional; must parse as a valid ISO date if present.

## Frontend state machine (app.js)

State = `{ tasks, search, statusFilter, priorityFilter, sortBy, sortDir }`.
Any change to search/filter/sort re-fetches `GET /api/tasks` with the
corresponding query string rather than filtering client-side, so the backend
remains the single source of truth for list semantics (testable via API
tests, TM-TASK-008).
