# Implementation Plan

## Approach

Single-user web app. Node.js + Express backend, SQLite (Node's built-in
`node:sqlite`) for persistence, vanilla HTML/CSS/JS frontend served as static
files by the same Express process — one deployable process, no build/bundle
step required for the frontend, minimal dependency surface for a demo of this
scope. Backend and frontend are still separate, versioned components per the
capstone's "front end + back end" requirement.

## Sequence

1. **Database** — `backend/db/schema.sql` defines the `tasks` table with the
   new columns (`status`, `priority`, `due_date`) up front, so no migration
   step is needed for a from-scratch build.
2. **Backend API** — REST endpoints for CRUD + reopen + search/filter/sort
   query params (implements TM-101…TM-109).
3. **Frontend** — single page, fetch-based, renders list + edit form + search/filter/sort controls.
4. **Tests** — Gherkin feature files (business-readable spec) + Playwright E2E
   specs that automate those same scenarios against the running app
   (TM-TASK-008).
5. **Non-functional pass** — keyboard nav, labels, basic pagination
   threshold, and user-facing error handling for API failures
   (TM-TASK-009).
6. **Build** — `scripts/build.ps1` runs the test suite, then packages backend
   + frontend into `dist/task-manager-build.zip` as the deployable artifact.
7. **Deployment** — `npm start` runs the packaged app locally on
   `http://localhost:3000`.

## Risks / decisions log

- No native DB dependency (`node:sqlite`) chosen over `better-sqlite3`/`sqlite3`
  to avoid native-module install issues on a locked-down machine with no
  pre-existing build tools.
- Vanilla JS frontend chosen over a React build pipeline to minimize
  dependency count and eliminate a bundler as a failure point, given the
  environment had no Node.js/npm pre-installed at project start (see
  [confluence/architecture.md](confluence/architecture.md) "Constraints").
